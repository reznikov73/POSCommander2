================================================================
1. ЦЕЛЬ И КРИТЕРИИ
================================================================
Файловый менеджер, максимально близкий к Total Commander по функциям и компоновке.
Приоритеты: скорость работы, скорость запуска, малый расход памяти. Иконки могут отличаться.

Замеры на этой машине:
  Показатель                  Total Commander   Avalonia-версия   POSCommander2 сейчас   Цель
  Запуск до окна              -                 1,4-2,7 с         76-118 мс              < 150 мс
  ОЗУ Working Set             32 МБ             170 МБ            15,5 МБ                < 25 МБ
  ОЗУ Private                 11 МБ             150 МБ            4,1 МБ                 < 15 МБ
  Размер exe                  ~5 МБ             49 МБ             819 КБ                 < 3 МБ

Замеры текущей версии сделаны на пустом каркасе. После каждой вехи их нужно повторять.
Для 100 000 файлов в каталоге бюджет не измерен (см. веху 4).

================================================================
2. ПРАВИЛО РАБОТЫ
================================================================
Каждый шаг короткий и заканчивается видимым результатом:
  1) правка кода;  2) сборка;  3) запуск;  4) скриншот или замер;  5) отчёт.
Нет шага больше ~30 минут без сборки. Нет проектирования "в уме" без файлов на диске.
Ошибки сборки и запуска исправляются сразу, отчёт идёт после них.

      Копирование, перемещение и удаление идут через COM IFileOperation: системный прогресс
      с паузой и отменой, конфликты решает оболочка (заменить/пропустить/отмена).
      SHFileOperation остался резервом, если COM недоступен, и основным путём для --selftest
      (там нужен режим без диалогов).
      Проверено в живом окне: копирование 2 МБ -> 'IFileOperation perform hr=0 aborted=0',
      файл в целевой папке; удаление -> 'Delete perform hr=0', файл ушёл в корзину.
  5.1 Конфликты: диалог оболочки (проверено косвенно: при цели, равной источнику,

  5.2 Ошибка на одном файле не останавливает очередь: элементы ставятся в очередь по одному,
      сбой одного помечает операцию неуспешной, остальные продолжаются.
  5.3 Очередь операций — СДЕЛАНО 08.11.2026.

    2. Ошибка в раскладке — это порча памяти в нашем процессе, а не аккуратная ошибка.
       Правильное решение (процесс-хост с IPC) не спасает функциональность без верных структур.

       Выгода для этого проекта — умеренная: архивы уже закрыты через 7z.exe (веха 8).
    4. Риск для готового продукта: падение плагина внутри процесса ломает весь менеджер.

    - держать плагины в отдельном процессе-хосте с простым протоколом (список/распаковка);
